# Usage log

What the add-in's usage log records, how to read it, what has been settled and what is still open. Code: `worker/src/usage-log.js` (the one writer both Workers use), wired into `worker/src/index.js` (the CORS proxy) and `worker-images/src/index.js` (the image host). Schema: `worker/migrations/`. Report: `scripts/usage-report.mjs`. Tests: `npm test` in `worker/` and in `worker-images/`. Built and live 2026-11-08, on top of the call log both Workers kept since 2026-10-23.

## What is recorded

- One table, `calls`, in the D1 database `apollo-addin-calls` named in both `wrangler.toml` files, shared by both Workers (`worker` = `proxy` or `images`).
- The proxy: one row per proxied Apollo call, that is every request except a CORS preflight (`OPTIONS`) and `/` or `/health`, which stay unlogged as before. Written twice: a `started` row when the request arrives and the full row when the reply is handed back, an upsert on `call_id`, so a call that never finished stays `started` (the report shows one older than 15 minutes as interrupted).
- The image host: one row per upload (`POST /img`), written the same two ways, and one row per failed request (a missing or malformed image, any other path), written only when it has failed. A successful image fetch writes nothing at all, not even a `started` row, because each one is a recipient opening an email and this log is not a read tracker; so a fetch that hangs leaves no row, by design.
- Every row: `call_id` (UUID), `ts` (start time), `worker`, `method`, `endpoint`, `outcome` (`started`, `success`, `error`), `version` (the Worker version from `CF_VERSION_METADATA`), `caller`, `has_key` (1 when an `X-Api-Key` header was sent, never the key), `status` (what the Worker answered), `ms` (from the request's arrival to the reply being handed back), `upstream_ms` (Apollo's time).
- `endpoint` is a path shape, never the raw path: the words of the Apollo endpoints the add-in calls and the image route are kept (`PATH_WORDS` in `usage-log.js`), a 24-hex Apollo record id or a 32-hex image key becomes `{id}`, and any other segment becomes `?`, so a name, an email address or a search term in a path can never reach a row. The query string is never read. Paths with more than eight segments are stored as `?`.
- `caller` is a class worked out from the request's `Origin` header, never the header's value: `outlook-addin` (the add-in's own GitHub Pages origin, where the task pane runs), `office-host` (one of the Microsoft hosts both Workers already allow), `other-origin` (any other origin), `no-origin` (no header: a script, `curl`, a server). Origin is what the client claims: a browser always sets it truthfully, but a script can send anything, so the class says what the request showed, not who sent it.
- No person can be named. Each teammate enters their own Apollo key in the add-in, and the key is the only thing that tells teammates apart; using it in any form (a hash, a fragment, a lookup of whose key it is) would put an identifier for a person in the log, so it is never read for the log beyond whether the header was present.
- Outcome rule for the proxy, a pass-through: `success` when Apollo answered below 400, `error` when Apollo answered 400 or above (the proxy passed the error on, `reply_reason` `apollo_status`) or could not be reached (the proxy's own 502, `reply_reason` `upstream_fetch_failed`, `failure_category` `upstream_error`). `failure_category` comes from Apollo's status by a fixed mapping (`categoryOfStatus`): 401 and 403 `authentication`, 429 `rate_limit`, 408, 504 and 524 `upstream_timeout`, any other 4xx `input_validation` (Apollo refused the request as sent), 5xx `upstream_error`. A request that throws inside the Worker is rethrown unchanged and leaves `error`, `internal`, `thrown`.
- The image host's own fields: `reply_reason` is its own fixed error code (`unsupported_content_type`, `too_large`, `empty_body`, `content_mismatch`, `not_found`, `quota_exceeded`, `invalid_api_key`, or `thrown`), each with a fixed `failure_category`; `key_check` is the upload gate's result: `no_key`, `no_team_config` (the firm team id is not configured), `unreachable` (Apollo could not be reached), `rejected` (Apollo refused the key), `unreadable` (Apollo's answer was not JSON), `not_firm` (a working key from another Apollo team), `firm`. Every value but `firm` still answers the same `401 invalid_api_key` as before; the code only says why, so an Apollo outage no longer looks like a bad key. `upstream_status` and `upstream_ms` are Apollo's status and time for that check (`/v1/users/api_profile`). `content_type` is the declared type when it is one the host accepts, else `?`; `upload_bytes` the body's size in bytes once read; `deduped` whether identical bytes were already stored.
- Not stored, ever: the Apollo key or any part or hash of it, a request or reply body, a query string, an email address, an image, its hash or its public key, the `Origin` value, cookies, or any error text. Every text column is re-checked against a fixed list or a strict pattern before it is written (`sanitizeRow`), and anything else is stored as `?`. Tests feed keys, emails, bodies, queries and error text through both Workers and check none of it reaches a row.
- Rows written before 2026-11-08 have no `call_id` and keep their old meaning: on the proxy `ms` was Apollo's time, `endpoint` was the raw path, and `detail` could hold an error code; the report counts them and never times them. They are pruned after the 90 days they were promised; new rows are kept 365 days. Either Worker prunes on 1% of its finished writes.
- Delivery health, outside D1: one point per log write in the Analytics Engine dataset `apollo_addin_usage_health` (binding `USAGE_HEALTH` on both Workers): which Worker, which write (`start` or `finish`), its result (`written`, `lost`, or `no_binding` when the D1 binding is missing) and the version. Nothing else.
- Logging never delays, fails or changes a reply: both writes run in `waitUntil`, the finish after a timer tick, every error is swallowed, and the tests prove every reply byte-identical with logging on, off, failing, hanging and with no `waitUntil` at all, and identical to the Workers' replies before this log when pointed at a copy of the old code (`PROXY_ORACLE`, `IMAGES_ORACLE`).
- Workers Logs stays off in both `wrangler.toml` files: it records request headers, and every request here carries a teammate's Apollo key.

## How to read it

- `node scripts/usage-report.mjs [--days N] [--tool proxy|images|<path shape>]` from the repo root, with a Cloudflare token in `CLOUDFLARE_API_TOKEN` that can read the Workers' D1 (`npm ci` in `worker/` first on a fresh checkout). Read-only. Sections: calls per endpoint and outcome, callers, total against Apollo time, the version comparison by workload band, failures by category, reason, status and key check, calls that never finished, the slowest calls, rows from before this log, then the performance log. Every percentile prints its count, and below 5 successful calls it prints "too few calls" (`docs/PERFORMANCE_LOG.md` says why 5). It exits 1 if the performance log is missing or malformed.
- `node scripts/usage-report.mjs --health` reads the Analytics Engine dataset (7 days) without D1 and exits 1 on any lost write or missing binding, and on any non-OK answer from Analytics Engine (a dataset that has never been written answers 200 with no rows, so an error is never read as "no writes"). Points take a minute or more to arrive and arrive in pieces. "No log writes recorded" means nobody used the add-in or the Workers cannot write health points; D1 rows in the same window mean the second.
- Ad hoc, from `worker/`: `./node_modules/.bin/wrangler d1 execute apollo-addin-calls --remote --command "SELECT ts, worker, method, endpoint, outcome, caller, status, ms, upstream_ms, failure_category, reply_reason, key_check FROM calls ORDER BY id DESC LIMIT 30"`.
- "Our time" is `ms - upstream_ms`. A Worker's clock only advances on I/O, so on the proxy it is the time spent reading the request body before forwarding it, and reads near 0; it is never CPU. Do not chase it.
- The proxy's `ms` ends when Apollo's headers arrive and the reply is handed back; the reply body then streams to the add-in and that part is not timed.
- `scripts/capture-replies.mjs <out.json> [--key-file <path>]` captures both Workers' replies to a fixed set of harmless requests (preflights, health, keyless calls, a missing image, refused uploads and, with a key file, one read-only `GET /v1/auth/health`), storing hashes and lengths only. Run it twice before a deploy to prove the capture is stable, then after, and diff.

## Settled

- 2026-11-08, before the build: each live Worker bundle was byte-identical to a dry-run build of `main`, so the deploy changed nothing but the log. Switching both `package.json` files to `"type": "module"` (so the tests can import the Workers) left both bundles byte-identical.
- 2026-11-08, the offline proof: against the Workers as they were on `main`, run from a copy outside the repo, the new code with logging on gave byte-identical replies (status, status text, every header, body) to 17 proxy requests and 18 image-host requests, and a one-byte change in either old copy made the test fail.
- 2026-11-08, real runtime: both Workers under local `wrangler dev` on one local D1 with both migrations wrote one complete row per logged request (versions set, no `started` left), and gave the same status, status text and body as the live Workers to all 14 capture requests; only `date` and `content-length` differed, which the edge sets.
- 2026-11-08, live: `scripts/capture-replies.mjs` captured 14 replies twice before the deploy (identical both times), once more after the migration was applied (identical: the old code kept answering and inserting its seven-column rows), and again after each Worker's deploy: all 14 identical to the first capture, headers included (volatile edge and request-id headers masked). The capture made one read-only `GET /v1/auth/health` with a key, with and without the add-in's Origin, and no Apollo write and no upload.
- 2026-11-08, live rows: every request the capture sent after the deploy left one complete row on the new versions (proxy `outlook-addin` and `no-origin`, with and without a key; the image host's missing and malformed image, its unsupported-type and keyless uploads), no row stayed `started`, no successful image fetch was involved, and `node scripts/usage-report.mjs` read them all.
- 2026-11-08, keyless proxied calls: Apollo answers `GET /v1/auth/health` with 200 with or without a key, and `GET /v1/email_accounts` without a key with 422, not 401 (`learnings.md`). So a keyless call can log as `success` or as `input_validation` rather than `authentication`; read `has_key` before calling a 422 a bad request.

## Open problems

- No person can be named, by design (see `caller`). If per-person use ever matters, it would need the add-in to send a per-person identifier the teammate agreed to, a change to the served add-in that this release did not make.
- `Origin` can be forged by anything that is not a browser, so `outlook-addin` means "claimed to be the add-in". Every call still needs a working Apollo key, which is what actually gates use.
- A client that disconnects mid-call leaves its row `started`; the report shows it as interrupted after 15 minutes. The log does not tell a disconnect from a Worker that was stopped.
- A hanging image fetch leaves no row, by design (no `started` row for image fetches).
- As of 2026-11-08 no real push from Outlook had passed through the new versions: every `outlook-addin` row so far came from the capture script sending the add-in's Origin. That real task-pane calls arrive as `outlook-addin` follows from where the task pane is served; the first real push confirms it.
- `usage-log.js` keeps its own copy of the Microsoft origins both Workers allow (for `office-host`). A host added to a Worker's allowlist and not there would log as `other-origin`; change both together.
